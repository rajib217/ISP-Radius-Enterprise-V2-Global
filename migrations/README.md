# Database migrations

## Baseline

- Target: PostgreSQL 16 or newer.
- Apply every numbered migration from 0001 through 0015 in filename order.
- These migrations assume an empty database for the baseline. Migrations 0013 through 0015 are additive and do not rewrite subscriber or financial data.
- Take and verify a backup before applying migrations to any non-empty environment.
- Apply each migration once, in filename order, using a database role limited to schema changes.
- The application role should not own tables or have permission to bypass tenant-scoped service access.

## Tenant isolation

Every tenant-owned record includes tenant_id and application queries must include the authenticated tenant ID. Do not trust a tenant ID supplied by a browser/client. Operator sessions reference an active tenant membership through a composite foreign key.

## Accounting invariants

Money uses NUMERIC(19,4), never floating point. A posted journal is checked at transaction commit for at least two lines, one currency, and equal debit/credit totals. Lines become immutable once the journal is posted or reversed. Corrections use a separate linked reversal.

Post in one database transaction: insert draft header, insert all lines, update status to posted, then commit. A failure rolls back the entire transaction. A reversal workflow must also lock and verify the original journal, ensure it has not already been reversed, insert the reversing draft, and update the original state atomically.

## Accounting event and session lifecycle

Migration 0002 stores normalized accounting events with tenant-scoped idempotency. Migration 0003 adds the current subscriber-session projection, keyed by tenant, NAS identifier, and RADIUS session ID. Start, Interim-Update, and Stop events are applied in the same caller-owned transaction as the event insert. Older events cannot move the projection backwards, and a stopped session is terminal for that session key. Interim-Update received before Start can create an active projection with an unknown start time.

## Usage metering

Migration 0012 stores idempotent usage deltas linked to immutable accounting events. Deltas are metering evidence only; they do not price usage, create invoices, or post financial entries.

## Subscriber authentication and authorization

Migration 0004 adds one Argon2id password hash per tenant-scoped subscriber. The initial FreeRADIUS integration is PAP-only over a protected REST/HTTPS channel. NAS source identity is resolved server-side and no plaintext subscriber password is stored.

## CoA and Disconnect outbox

The tenant-scoped outbox, fenced worker leases, retry policy and RFC 5176 UDP transport are implemented. Operator API authentication/RBAC and live NAS interoperability tests remain incomplete. Do not represent an enqueued command as a completed disconnect or applied policy change.

## Operator identity foundation (migration 0013)

- `operator_users` stores normalized lowercase email addresses and Argon2id password hashes. Email uniqueness is case-insensitive.
- `operator_tenant_memberships` assigns one tenant-scoped role per user. The role is a coarse assignment; application authorization must map it to explicit permissions and deny by default.
- `operator_sessions` stores only SHA-256 digests of high-entropy opaque session and CSRF tokens. Raw tokens must be generated by the application, returned only where required, and never logged or persisted.
- Sessions are bound to a tenant membership. Every request must re-check user status, membership status and expiry/revocation. Revoking or suspending a user or membership must invalidate access even if a session row remains.
- `operator_audit_events` is append-only at the database trigger level. Never put passwords, raw tokens, cookies, RADIUS secrets or payment credentials in metadata.
- The application implements `/operator/login`, `/operator/session` and `/operator/logout`, opaque HttpOnly cookie sessions, CSRF double-submit validation, origin allowlisting, login throttling, server-side session revocation and role-to-permission mapping. A read-only monitoring BFF with `sessions:read` enforcement is implemented. Permission enforcement for future write routes, MFA and recovery flows remain pending.

## Operator login throttling (migration 0014)

- Failed attempts are counted by SHA-256 hashes of the normalized email/IP pair and remote IP, never by storing the raw email/IP in the throttle table.
- Five failures in a rolling 15-minute window lock the matching email and IP scopes for 15 minutes. Successful authentication clears both scopes.
- This is a baseline distributed throttle. Deployments behind reverse proxies must configure trusted proxy handling so the remote IP represents the actual client, not an untrusted forwarded header.

## Important scope

This is a foundational schema, not a complete billing or statutory accounting implementation. It does not yet include invoices, payment allocation, taxes, fiscal-period close, a production RADIUS listener, or a migration runner. Validate SQL, locking behavior, concurrent event ingestion, and privilege boundaries against the exact PostgreSQL version in staging before production use.


## Operator MFA persistence foundation (migration 0015)

- WebAuthn records store credential IDs, public keys and authenticator metadata only.
- TOTP records store AES-GCM ciphertext, a 12-byte nonce and an external KMS key version. Do not activate a factor until enrollment verification succeeds. A partial unique index permits one active TOTP factor per user.
- MFA challenges store only a SHA-256 digest, are bound to method, exact origin and RP ID, and have a database-enforced maximum five-minute lifetime. Conditional updates provide one-time challenge consumption and bounded failures.
- Recovery codes store only SHA-256 digests and are consumed with a conditional update. Generate high-entropy codes and display them once.
- Factor reset must revoke all outstanding challenges and active operator sessions in the same database transaction.
- Migration 0015 adds storage and repository primitives only. It does not change the login flow or enforce MFA. Complete cryptographic verification, KMS integration, recovery approvals and PostgreSQL concurrency tests before enabling MFA.

## 0016: TOTP wrapped data key

Adds the KMS-wrapped AES-256 data key to operator TOTP factor records. TOTP
secrets are encrypted with AES-256-GCM using a fresh data key and nonce; the
wrapped data key is stored separately and can only be unwrapped by the configured
KMS provider. Migration 0016 is additive and precedes any TOTP enrollment flow.


## 0017: Tenant-bound operator login MFA challenges

Adds an optional tenant reference to MFA challenges. Login challenges must bind
the selected tenant at password-authentication time so the assertion response
cannot choose or switch tenant membership. Enrollment challenges leave this
field NULL. Existing challenges remain valid and are not rewritten.
